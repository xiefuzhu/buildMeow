### Structure, as verified by reading the file

The root object maps a colour index (`"0"` .. `"60"`, 61 entries) to:

- `tonesRGB` — four pre-computed map colours for that base colour:
  - `light` — **this is the base colour itself**, i.e. the 255/255 tone.
    A block shows this tone when it is *higher* than the block to its north.
  - `normal` — the 220/255 tone. Block is the *same* height as its northern
    neighbour.
  - `dark` — the 180/255 tone. Block is *lower* than its northern neighbour.
  - `unobtainable` — the 135/255 tone. Only reachable under water, so
    staircase mapart never produces it.
- `blocks` — candidate blocks that produce this colour, keyed by a per-colour
  `blockId`. Each carries `displayName`, `validVersions`, `supportBlockMandatory`,
  `flammable` and `presetIndex`.
- `mapdatId` — the id used in map `.dat` files.
- `colourName` — upstream's human-readable name.

`validVersions` maps a Minecraft version to either `{NBTName, NBTArgs}` or a
string of the form `"&1.13.2"`, meaning "same as that version". References must
be followed to resolve a block state for a given version.

`NBTArgs` are the block state properties to emit, e.g. `{"axis":"y"}` for a
log. An empty object means "emit the block's default state".

Upstream's `validVersions` keys stop at **1.20**; there is no 1.21 entry.
The 1.21.x versions in `versions.json` therefore resolve their blocks through
`blockSetAlias: "1.20"`.

### Verified colour arithmetic

Every `tonesRGB` value satisfies `floor(base * factor)` where `base` is the
`light` tone and the factors are `220/255`, `180/255` and `135/255`:

```
light        = [127, 178,  56]
floor(127*220/255), floor(178*220/255), floor(56*220/255) = [109, 153, 48]  == normal
floor(127*180/255), floor(178*180/255), floor(56*180/255) = [ 89, 125, 39]  == dark
floor(127*135/255), floor(178*135/255), floor(56*135/255) = [ 67,  94, 29]  == unobtainable
```

`test/color_table_test.dart` asserts this for all 61 colours. This is what ties
the vendored table to the shade rule that staircase mapart depends on.

### Representative blocks

`lib/src/palette.dart` has two shapes of palette:

- `Palette.select` picks one representative per colour using only
  `supportBlockMandatory == false` candidates, preferring non-flammable ones and
  then the lowest `presetIndex`. Colour index 10 (`Water`) has **no** usable
  candidate — its only entry is the fluid, which upstream itself marks
  unsupported — so it is reported as unavailable rather than guessed at. 60
  colours, 60 blocks.
- `Palette.blocks` lists **every** candidate block of every colour: 209 entries
  across the 60 colours for the 1.20 block set, or 323 across all 61 when
  `includeSupportBlocks` is set. Within each colour the `select` winner is listed
  first, so the two palettes quantize to the same image until a block is
  switched off. This is what the app shows, grouped by colour, so the user picks
  what each colour is built from.

## `versions.json`

**Ours, not upstream.** See the `note` field inside the file. The
1.12.2–1.20 `dataVersion` values come from upstream's
`src/components/mapart/json/supportedVersions.json`. The 1.21.x values
(3953, 3955, 4080, 4082, 4189, 4325, 4435, 4438, 4440) come from the
`mcdata` crate's `data_version` module, cross-checked against the Minecraft
Wiki data version table.

World height limits are per version because 1.17 raised the overworld from
`0..255` to `-64..319`.

Nothing in this directory has been verified by loading an exported file into
Minecraft. See the "未验证 / Not verified" section of the root README.

## Production capability data

`block_capabilities.json` is generated by `dart run tool/gen_block_capabilities.dart`
from the retained game-constructor dump and texture-palette metadata. It records
unavailable candidates, known block IDs, and the states used to extract top-face
textures. It adds no new textures or upstream colour values. The application's
production resolver uses these records; the low-level legacy palette APIs above
remain available for diagnostics and compatibility.

The current `versions.json` targets only **26.1.2**, using data version **4790**
from that client's `version.json`. Earlier-version discussion above is historical.
